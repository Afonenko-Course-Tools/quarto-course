# Совместная проверка плана изменений

Проверка выполнена 6 октября 2026 года по [полному плану](course-change-plan.md), [обзору идентичности](../quarto-course/docs/plans/course-identity-review.md), текущим исходникам и первичным документам Quarto, GitHub и Task. Три независимых обзора охватили идентичность и экспорт, презентации и профили, публикацию и получение ресурсов. Их выводы сопоставлены между собой.

Основные направления совместимы: нативная разметка Quarto, необязательный корневой Course ID, простой список подпроектов, единая публичная презентация, минимальные демонстрации рядом с расширениями, готовые результаты в Releases и небольшой Taskfile. Выявленные архитектурные противоречия разрешены последующим обсуждением. Детали интерфейсов, фактический граф зависимостей и минимальная матрица проверок определяются при начальном анализе актуальных репозиториев.

## Результаты проверки и статус решений

### 1 Область экспортной уникальности

Первоначальный обзор обнаружил, что требование уникальности по всему курсу не определяло число экспортных книг. Две разные книги могли бы дать один `course.id/exr-backup` при раздельном экспорте.

Также нужно определить идентичность работ: нынешний [body producer](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/body-export/producer.ts:181) формирует `owner/work.id`. Совпадение Exercise ID — не единственный возможный конфликт.

**Решено:** поддерживается один экспортный банк заданий и работ на курс. Его путь выбирается при запуске экспорта; отдельный bank.id не вводится. ID экспортируемых заданий и работ проверяются в этой книге. Обычные книги, упражнения и решения других подпроектов сохраняют нативное поведение. Машинный учёт истории экспорта других книг с тем же Course ID не входит в выбранный простой контракт.

### 2 Исходные данные экспорта и проекции student/full

Первоначальный обзор обнаружил зависимость экспорта от отфильтрованного рендера: в нём могли отсутствовать ответы. Нынешний [Core visibility](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/visibility.lua:96) также удаляет контрольные задания по роли. В уточнённом контракте участие отдельных контрольных файлов в student-сайте определяется списками профилей, а в LMS-поставке — полным исходным корпусом.

**Решено:** экспорт читает полные исходные данные выбранной работы и формирует результат по требованиям адаптера. Наличие опубликованной `full`-версии или подготовленного полного HTML для этого не требуется. Функциональные профили Quarto и выбранная конфигурация задания продолжают учитываться.

### 3 QRC-ссылки единой презентации

**Прежний вопрос снят после уточнения пользователя.** Общие задания имеют одни исходники, условия и устойчивые ID; full показывает решения и закрытые комментарии. Дополнительно пользователь определил отдельные контрольные `.qmd`, исключённые из student-списка и включённые в локальный full-site. Это явное исключение по составу файлов, не изменение условий общего задания.

Для полноценного курса публикуется студенческая версия; `full` на данном этапе собирается из исходников для локального просмотра и не публикуется рядом с ней. Для шаблона и демонстрационных проектов, напротив, задаётся `full` по умолчанию: специально подготовленные решения и комментарии показывают возможности инструментов и намеренно публичны.

Тип `control` сам по себе не должен удалять условие из HTML или экспортного пакета. Student-сайт и его QRC-каталог не содержат исключённых контрольных файлов; локальный full-каталог их содержит. Публичные материалы ссылаются на доступные общие задания, а не на исключённые контрольные. Неизменность номеров общих глав следует обеспечивать составом и порядком профилей, если это требуется; устойчивые ключи не зависят от номера.

### 4 Локальный просмотр неизменного готового HTML

План одновременно требует простого копирования готовых публикаций, отсутствия переписывания HTML/QRC и локального preview. Собственные QRC-цели имеют относительные ссылки и допускают перенос всей публикации. Но цели из импортированного каталога получают абсолютный `base-url`, который фиксируется в готовом HTML. Это видно в [QRC urls.ts](/home/tolya/Cybersecurity/task/_extensions/Afonenko-Course-Tools/reference-catalog/domain/urls.ts:2). При этом producer [не записывает baseUrl в экспортируемый каталог](/home/tolya/Cybersecurity/task/_extensions/Afonenko-Course-Tools/reference-catalog/domain/exports.ts:21).

Следовательно, сам QRC JSON не следует объявлять непереносимым. Привязка к публичному адресу появляется при разрешении внешнего импорта в HTML.

**Решено:** внутренние переходы готовой демонстрации локальны. Специальные примеры внешнего QRC при локальном просмотре могут вести в указанную публичную публикацию. Полного локального переназначения внешних ссылок не требуется. Карточки каталога ссылаются на локальные готовые демонстрации обычными относительными ссылками.

### 5 Стабильность Release и исправления демонстрации

Фиксированный URL сам по себе не гарантирует неизменность файла: mutable Release позволяет заменить asset по тому же адресу. Это влияет на соответствие показанного результата и выбранных исходников.

GitHub предоставляет штатные [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases): связанные assets и тег нельзя изменять после публикации. Все файлы сначала прикладываются к draft, затем выпуск публикуется. Это позволяет обеспечить стабильность без собственного менеджера.

**Решено:** использовать неизменяемые Releases. Разрешены отдельные Releases демонстраций в том же репозитории с явно указанными версиями расширений. Taskfile содержит точный URL и не разрешает зависимости и не интерпретирует тип выпуска.

### 6 Общие исходники и достаточная GitHub-папка

План одновременно предлагает хранить повторяющиеся фрагменты в одном месте и проверять полученную папку примера в чистом окружении. Если `examples/java-gradle/` подключает `../common/statement.qmd`, одной ссылки на первую папку недостаточно для воспроизведения.

**Решено:** самостоятельная единица исходников — папка группы с одним небольшим демонстрационным курсом, общим банком заданий и ресурсами, несколькими сценариями. Штатная GitHub-ссылка ведёт на всю группу. Все учебные исходники группы находятся внутри её папки; общие учебные зависимости между группами и репозиториями не вводятся.

Согласованный пример будущей структуры: в `quarto-course-print/examples/paper/` располагается один маленький демонстрационный book-проект. `topics/checksum.qmd` хранит общие задания; `handouts/checksum.qmd` — страницу раздатки с `.task-items`; `controls/control-01/tasks.qmd` — собственные задания контрольной; `variant-01.qmd` и `variant-02.qmd` — отдельные назначения вариантов; общие изображения находятся в `assets/`. Раздатка и контрольные — разные демонстрационные сценарии этого проекта. У каждого задания одно объявление в своём тематическом/контрольном источнике. Всё необходимое учебное дерево находится внутри `examples/paper/`; source-ссылка ведёт туда. Получение только `handouts/` не считается получением самостоятельного проекта. Эта структура описывает архитектурное решение; файлы примера ещё не созданы.

Группа имеет одну веб-публикацию с отдельными страницами сценариев и PDF-результатами. Технические детали печатной конфигурации не фиксируются этим примером. Аналогичная самостоятельная группа Java/Gradle может содержать свой банк, несколько работ и один небольшой программный проект в репозитории PrairieLearn. Расширение устанавливается обычным способом отдельно от получения исходников группы. Разделение раздатки и контрольной на самостоятельные курсы с дублированием общих материалов отклонено.

### 7 Поиск внутри презентации

Граница центрального поиска документации уже согласована и не пересматривается. Но локальный поиск презентации пока исключает заметки и может находить текст свёрнутого ответа без раскрытия найденного блока. Нынешняя реализация находится в [navigation/model.js](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-navigation/navigation/model.js:38) и [navigation/ui.js](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-navigation/navigation/ui.js:169).

Варианты:

- Искать по основным слайдам, общим заметкам, подсказкам и решениям; переход раскрывает найденный блок.
- Искать только по основному содержанию слайдов.

**Решено:** искать по основному содержанию, общим заметкам, подсказкам и решениям; переход раскрывает найденный блок и нужных родителей. Это не означает включение демонстраций в центральный индекс сайта.

### 8 Формат подпроекта и переопределения отдельных документов

План выбирает один веб-формат из эффективной конфигурации подпроекта, но обычный website Quarto может содержать HTML-страницу и отдельный `.qmd` с `format: revealjs` в front matter. Ответ о сочетании HTML/PDF в конфигурации не означал согласия запретить такие переопределения. Сейчас [сборщик задаёт формат всему подпроекту через `--to`](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-site/application/compose.ts:91).

Варианты:

- Учитывать эффективную конфигурацию каждого документа: один выбранный веб-формат на документ, собственные переопределения и outputs Quarto. Для книг сохраняются нативные ограничения форматов самого book-проекта.
- Для составной сборки требовать одинаковый веб-формат у всех документов каждого подпроекта; разнородные документы выносить в разные подпроекты.

**Решено:** учитывать эффективный формат каждого документа с профилями и front matter. Website может сочетать HTML и Revealjs у разных документов. Для book сохраняются нативные ограничения форматов. Общий принудительный `--to` подпроекту должен быть пересмотрен.

## Редакционные исправления и следствия уже принятых решений

- Исправлена устаревшая запись о `practice`: текущая корневая конфигурация уже использует `seminars`.
- Убрана формулировка, которая считала любой живой пример упражнения в руководстве второй канонической декларацией. Независимый нативный пример вне экспорта допустим; согласованность поддерживаемых исходников остаётся организационной задачей.
- Уточнён критерий обычного рендера: нативные `sol-*` и заголовки не обязаны включать экспортную связь по суффиксу или `sec-*`. Связь ответа и задания проверяется в выбранной модели экспорта, не навязывается всем нативным элементам.
- Отсутствие контрольных заданий в презентации остаётся политикой материала, а не новым валидатором нативных упражнений.
- Крупный вид печатных слайдов и раскрытые ответы не требуют ровно одной страницы на слайд. Quarto допускает продолжение высокого слайда на нескольких страницах через `pdf-max-pages-per-slide`; при реализации нужно сохранить содержимое без обрезки. [Параметры печати Quarto](https://quarto.org/docs/presentations/revealjs/presenting.html#print-options). Ограничение одной страницей не было принято.
- Архив готового рендера в Release и отказ от собственной ZIP-упаковки исходников курса совместимы. Для ясности различаются результат публикации и получение исходников по GitHub-ссылке.
- Поддержка Task на трёх ОС не считается проверкой вызываемых утилит; необходимые проверки уже входят в план.

## Уточнение о контрольных файлах и платформенной поставке

Пользователь уточнил отдельный тип контрольного задания и отдельные `.qmd` для таких материалов. Списки профилей задают состав сайта: student исключает контрольные файлы, локальный full включает их задания, решения и комментарии. Для курса кибербезопасности предусматривается локальный рендер вариантов контрольных. Согласованы общая страница заданий контрольной и отдельный QMD каждого варианта со своим ID и фиксированным составом.

Для book штатный сценарий Quarto — полные списки `book.chapters` в каждом профиле без общего списка в `_quarto.yml`. Временный пример проверен через `quarto inspect`: сокращённый student-список при общем базовом списке не исключил контрольную из inputs; разделённые профильные списки обеспечивают требуемый состав. [Профили Quarto](https://quarto.org/docs/projects/profiles.html#profile-groups).

Платформенный экспорт получает контрольные из полного исходного корпуса, независимо от наличия их HTML на открытом сайте. Доступ к работе и показ ответов относятся к LMS. В текущем Core [filter.lua](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/filter.lua:22) создаёт public-тела через student-фильтрацию, а [producer.ts](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/body-export/producer.ts:106) использует их в пакете. Значение «условие для участника LMS» нужно отделить от «страница включена в открытый student-сайт».

PrairieLearn предоставляет штатный `accessControl` для assessment; `allowAccess` обозначен как legacy. [Современная модель доступа](https://docs.prairielearn.com/assessment/accessControl/).

Moodle XML переносит вопросы, но не создаёт деятельность «Тест» и её правила доступа. Точный [экспортёр шаблона v1.0.0](https://github.com/Afonenko-Course-Tools/quarto-template-course/blob/v1.0.0/_extensions/Afonenko-Course-Tools/course-moodle/application/export.ts) формирует вопросы из `p.questions`, не создавая работы из `p.works`. **Решено:** сейчас прорабатываем модель и требуем минимум от экспорта вопросов. Автоматическое создание деятельности и её настройка не входят в текущий объём. [XML вопросов](https://docs.moodle.org/502/en/Moodle_XML_format), [настройки теста](https://docs.moodle.org/502/en/Quiz_settings).

Состав ресурсов должен соответствовать файлам профиля: исключение `.qmd` само по себе не исключает все изображения, вложения и локальные экспортные пакеты из общего resources-glob. Это проверка изоляции студенческой публикации, а не новая система доступа.

## Условия внедрения и актуальный статус

Первый пакет завершён: один экспортный банк и полный исходный вход экспорта согласованы; прежний вопрос о разных условиях задач снят. Локальность внешних QRC-переходов, неизменяемость Releases и независимые выпуски демонстраций также согласованы. Затем согласованы общий `.task-items`, отдельные QMD вариантов контрольных и ссылочный первый веб-интерфейс со штатным предпросмотром. Inline отложен; дополнительные задания не заменяют обязательные; правила оценки всегда платформенно специфичны и общей модели оценки не будет. Последний пакет согласовал форматы отдельных документов, поиск по всему публичному содержимому презентации с раскрытием цели и минимальные требования к экспорту Moodle на этапе проработки модели. Затем приняты обязательность заданий лабораторных и контрольных по умолчанию и папка группы с одним небольшим демонстрационным курсом как самостоятельная единица исходников. Дополнительное исследование приведено в [обзоре заданий](../quarto-course/docs/plans/assignment-display-review.md). Для специальностей приняты отдельные QMD-страницы работ с собственными ID и явными назначениями из общего банка. Маршруты специальностей ссылаются на соответствующие работы. Публикация документации согласована: ручной локальный сценарий через Taskfile, явное получение закреплённых готовых демонстраций, рендер и проверка, затем `quarto publish gh-pages --no-render`. Принята однократная миграция без поддержки старых YAML, конфигураций и QMD. Поддерживается только актуальный авторский формат; теги инструментов и закреплённые релизы сохраняются для воспроизводимости. Исходная база — последние актуальные версионные ветки инструментов. Точная запись назначений, фактический граф зависимостей и минимальная матрица проверок уточняются при начальном анализе архитектуры.

Принятые решения отмечены явно; остальные предложения обзора требуют дальнейшего обсуждения. Исходники расширений и конфигурации курса при проверке не изменялись.

Согласованный маршрут внедрения начинается с обновления локальных репозиториев, анализа архитектуры и организации кода, затем необходимого рефакторинга. Инструменты обновляются по зависимостям с согласованной документацией, PR, слияниями в `main`, новыми версиями и тегами. Все артефакты готовятся до публикации неизменяемых Releases. Шаблон перестраивается и проверяется локально без публикации на GitHub Pages. После этого курс кибербезопасности переводится на новые закреплённые релизы стандартным механизмом Quarto на свежей ветке, и создаётся PR.

Фильтры и разметка сохраняют минимализм надстройки. Существующие функции Quarto переиспользуются через публичные API; документация, спецификации, README, схемы и примеры обновляются вместе с соответствующим кодом. Порядок выпуска и границы текущего внедрения приведены в [основном плане](course-change-plan.md).
