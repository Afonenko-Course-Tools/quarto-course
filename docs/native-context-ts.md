# Загрузка `course-project`

Core загружает только пространство имён `course-project` для каталогов кода.
Метаданные настоящих документов, заголовки, условия, исполняемые ячейки и выбор
профилей обрабатывает Quarto. Загрузчик не создаёт документы для каталогов
проектов.

`readProjectContexts([{owner, directories, profiles, format}], callback)` читает
каждый участвующий YAML один раз за операцию. `directories` — относительные к
`owner` каталоги кодовых проектов. `profiles` — фактически выбранные профили из
композиции Quarto; выбор значений по умолчанию, групп и dotenv не повторяется.
Внутри операции Quarto методы `withProjectContexts` и `withProjectContracts`
используют одинаковый договор.

Контекст содержит `{owner, input, profiles, format, contract}`. Здесь `input` —
абсолютный каталог кодового проекта; пути в `contract` тоже абсолютные.
`decodeProjectContract(context)` возвращает этот договор. Контекст и план
действуют в пределах обработчика; сериализация не передаёт право чтения файлов.
Неизменность исходников между вызовами не проверяется и не обещается.

## Слои и объединение

Порядок от менее приоритетного к более приоритетному:

1. `_quarto.yml` либо `.yaml`, затем его `metadata-file`/`metadata-files` в
   порядке списка, поверх объявления основного файла.
2. Фактически выбранные `_quarto-<profile>.yml`/`.yaml` в обратном порядке
   списка: первый перечисленный профиль выигрывает конфликт скалярных значений.
3. `_quarto.yml.local` либо `.yaml.local`.
4. `_metadata.yml`/`.yaml` от `owner` к конечному каталогу, включая его самого.

Включения в метаданных каталогов поддерживаются тем же явным прикладным
правилом: рекурсивно в порядке списка, с отказом при цикле. Каждый включённый
файл является собственной базой `base: config`. В профилях и `.local` включения
метаданных не применяются, как при композиции профилей Quarto. В каждом слое
обычный `course-project` дополняется `format.<selected>.course-project`. Это
ограниченный договор пространства имён, а не воспроизведение всех стадий
метаданных Quarto.

Карты объединяются по ключам, скалярное значение заменяется, `false`
сохраняется. Предметная схема использует карты и скалярные значения; массив в
этих полях отклоняется декодером. Явный `course-project: null` также
отклоняется. Псевдонимы и теги разбирает обычный YAML-парсер; псевдоним адреса
нормализуется один раз. Дерево CST, маркеры и DTO происхождения не создаются.
При наличии обоих расширений имени выбирается `.yml`.

## Адреса

Все адреса starter, components, testsets, solutions, instructions и значения
`build.files` имеют одинаковый вид:

```yaml
course-project:
  starter: { path: starter }
  components:
    support: { path: common/java/api-support, base: config }
  build:
    files:
      settings.gradle: { path: common/settings.gradle, base: config }
```

Обычный адрес относится к конечному кодовому проекту. `base: config` относится к
YAML, который объявил адрес. Адрес `path`/`base` заменяется атомарно:
переопределение `{path: local}` снова относится к проекту даже после
унаследованного `base: config`. Остальные поля узла, например `requires`,
объединяются независимо.

База не выбирается по существованию файлов. Отсутствующий выбранный путь даёт
`PROJECT_PATH_MISSING` с адресом и полем. Выход из `owner`, служебный кеш,
символические ссылки и специальные типы файлов отвергаются. При материализации
обходятся выбранные деревья; байты читаются по необходимости. Приватные роли
файлов, коллизии конечных путей и новый безопасный каталог назначения
проверяются отдельно.

Метрики: `yamlFileReads`, `yamlBytesRead`, `directoryLayers`, `sourceFileReads`,
`sourceBytesRead`. Последовательные пакетные обращения одной операции
переиспользуют разобранные значения YAML; счётчики следующего пакета показывают
только новую работу. Собственных снимков исходников, хеширования дерева и
проверок неизменности нет. Ограниченный пример не подтверждает скорость всего
курса или готовность установленной композиции.
