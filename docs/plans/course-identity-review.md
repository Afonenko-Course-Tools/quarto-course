# Идентичность курса и семантика упражнений Quarto

`course.id` в текущей поставке — внутреннее имя владельца модели и экспортируемых объектов. Оно не является нативным ID курса PrairieLearn или Moodle. Однако Core требует его значительно раньше экспорта, а значение `exr-*` связывает с обязательной моделью канонического задания. Перенос ID только в книгу заданий не устраняет это смешение.

Запрет упражнений вне задачника был предложением при обсуждении нового плана, а не правилом Quarto. Предложение снято с рекомендуемого варианта. `subprojects` выбран как имя будущего простого списка вложенных проектов.

## Исходные предпосылки

Найденный [план общих инструментов](/home/tolya/course-tools/specs/quarto-tools-plan.md) проектировал строгую учебную модель внутри книг и слайдов: темы, канонические задачи, планы, работы, закрытые и публичные проекции, обмен между курсами. Он одновременно стремился сохранять штатную разметку Quarto.

В нём прямо заложены несколько решений:

- [Книга задач содержит все канонические упражнения, а каждая книга имеет владельца](/home/tolya/course-tools/specs/quarto-tools-plan.md:29).
- [Идентичность владельца, адресный namespace и путь источника различаются](/home/tolya/course-tools/specs/quarto-tools-plan.md:313). Перемещение файла и изменение транспорта не должны менять ключ объекта.
- [Идентичность записывается на уровне каталога книги](/home/tolya/course-tools/specs/quarto-tools-plan.md:315). Совпадающие локальные ID разных владельцев допустимы.
- [Общие task/work keys относятся к Core, платформенные ID, UUID и доставка — к адаптеру](/home/tolya/course-tools/specs/quarto-tools-plan.md:710).

Сам план не задаёт поле `course.id` и не требует равенства owner этому полю. Это выбор реализации. Смысл устойчивого ключа обоснован экспортом, переиспользованием и семантическими связями между источниками; из него не следует обязательность ID для оформления любого документа.

История локальных репозиториев показывает, что первоначальные Core и PrairieLearn создавались вместе: Core `202d397` уже требовал `course.id`, а PrairieLearn `9aaec64` описывал пару `course.id + exercise.id` для будущего компилятора. Это произошло до Moodle. История не доказывает, что ранняя общая модель была спроектирована независимо от PrairieLearn; она также не позволяет считать поле заимствованием из Moodle.

Позднее экспериментальный body producer принимал owner отдельно, а производственная реализация стала брать его из Course ID документов. Следовательно, необходимость owner в общем transport и конкретное место его задания — разные решения.

## Кто использует ID сейчас

Сведения ниже относятся к установленному Core и точной поставке шаблона `v1.0.0`. Соседние checkout поставщиков местами содержат более ранние контракты.

| Потребитель | Использование | Что это доказывает |
| --- | --- | --- |
| Core при обработке документа | Требует `course.id` при наличии `course:`, записывает его в факты и `sourceTopic.owner` | Обязательность сейчас установлена Core даже на странице без заданий. |
| Core при сборке модели | Проверяет одинаковый Course ID у документов одного выпуска | ID одновременно обозначает область сборки модели. |
| Body export Core | Записывает `package.owner`, ключи `owner/exr-id`, `owner/sec-id` и участников работ | Нужна устойчивая identity выбранного экспортируемого корпуса. |
| PrairieLearn | При стратегии `assignment.mode: assessment-id` вычисляет метку из пары Course ID и Assessment ID | Это конкретное использование ID адаптером; явная метка заменяет вычисление. |
| Cloud и PrairieLearn | Передают Course ID в конверте своих фактов для проверки соответствия Core | Адаптеры связаны общим протоколом; Cloud-модель ВМ и шагов сама не требует Course ID. |
| Moodle | Проверяет ключ общего пакета и записывает его в XML `name` и `idnumber` | Это отображение внутреннего ключа в экспорт, а не идентичность курса на сервере Moodle. |
| Print | Выбирает работу и её вопросы по ключам общего пакета | Нужна адресация работы в пакете, но не платформенный Course ID. |
| Course Site | Группирует факты Core по Course ID перед проверкой выпусков | Нужен из-за устройства модели; адрес размещения проекта определяется отдельно. |
| Project Download | Выбирает ресурс по source документа и ID задания | Прямого чтения Course ID нет; обычные объявленные ресурсы не требуют модели курса. |
| QRC, Presentation, Navigation | Используют собственные namespace, якоря и конфигурацию | Прямого использования Course ID для ссылок, нумерации или интерфейса не найдено. |

PrairieLearn использует собственные UUID вопросов, работ и экземпляров курса. Их стабильность при редактировании и перемещении описана в [документации платформы](https://docs.prairielearn.com/uuid/). Внутренний ключ нашего исходного объекта может помочь получать устойчивый UUID, но сама платформа не предписывает наличие `course.id` у всех исходных Quarto-проектов.

## Где смешались разные области

В шаблоне портал, теория, задачник и презентации имеют разные Course ID. Поэтому имя `course.id` фактически обозначает область модели нативного проекта или книги, хотя автор ожидает идентичность всего курса.

Простой перенос единого ID в корень тоже не является готовым исправлением. [Текущий release](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/domain/release.ts:54) требует одновременно одинаковые ID и формат документов; HTML и Revealjs одного логического курса не могут составить такую группу без изменения контракта. Вложенные Quarto-проекты также не наследуют автоматически метаданные корневого проекта.

Нужно различить:

1. Логический курс, объединяющий материалы.
2. Нативный проект Quarto с собственной конфигурацией и рендером.
3. Устойчивую identity исходного объекта при переиспользовании или экспорте.
4. Область одной сборки или пакета результатов.
5. Платформенные привязки и ID целевого сервера.

У этих понятий может быть общая связь, но равенство всех идентификаторов не следует из требований.

## Изменение смысла упражнений

Quarto определяет `exr-*` как упражнение, `exm-*` как пример и `sol-*` как решение. Это типы нумеруемых объектов со штатными ссылками. Документация не связывает упражнение с книгой задач или системой оценивания. [Нативные типы Quarto](https://quarto.org/docs/authoring/cross-references.html#theorems-and-proofs).

В [ранней спецификации учебных элементов](/home/tolya/course-tools/quarto-course/spec/learning-elements.md:52) `target` был явным признаком задания для оценивания. `exr-*` без `target` оставался обычным учебным элементом; роль и сложность были необязательными. Этот документ помогает понять первоначальный подход, но не описывает установленную сейчас поставку.

В установленном Core [каждый `exr-*` становится каноническим заданием](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/exercises.lua:4), получает `target="manual"` по умолчанию и [обязан иметь назначение, сложность и исходную тему](/home/tolya/Cybersecurity/_extensions/Afonenko-Course-Tools/course-core/native-document.lua:96). Обычное нативное упражнение из статьи или слайда тем самым включает дополнительные обязательства.

Правило «упражнение можно объявить только в задачнике» усилило бы этот сдвиг. Замена его на `exm-*` ради обхода проверки ещё и меняет содержательный тип: вопрос или упражнение превращается в пример. Поэтому ограничение места объявления исключено из рекомендуемого плана.

Разбор касается также других добавленных ограничений, например обязательного связывания `sol-*` по суффиксу и проверки всех атрибутов нативного Div. Дополнительное соглашение расширения должно включаться понятным автору способом и сохранять обычное поведение Quarto без такого соглашения.

## Принятое направление пересмотра

После обзора согласованы три решения: необязательный для обычного рендера `course.id` задаётся в корне курса и передаётся сборщиком в экспорт; состав выбранной работы определяет экспортируемые задания без дополнительного `target="manual"`; `course-role` и `difficulty` остаются необязательными, в том числе при экспорте. Эти решения описывают будущий контракт, а не уже изменённую реализацию.

### Обычная разметка

Нативные упражнения, примеры и решения разрешены в теории, задачнике, статье и презентации. Подключение оформления не должно само по себе превращать все упражнения в объект строгого экспорта. Дополнительные роли, сложность и время уточняют элемент, когда автор их указал.

### Организация курса

На курс поддерживается один экспортный банк — отдельная книга повторно используемых заданий и работ, путь которой выбирается при запуске экспорта. Теория и слайды могут ссылаться на условия через QRC. Обычные нативные упражнения других проектов допустимы.

Общие задачи имеют одни условия и устойчивые ID в `student/full`; полный профиль показывает решения и закрытые комментарии. Отдельные контрольные `.qmd` исключаются из student штатными списками профилей и включаются в локальный full-site. Тип `control` является классификацией, а не автоматическим правилом скрытия тела задания. Полноценный курс публикуется в студенческом виде, а `full` используется локально из исходников. У шаблона и демонстрационных проектов `full` задан по умолчанию для показа возможностей расширений.

### Модель и экспорт

Устойчивые ключи нужны объектам выбранного корпуса, который объединяется, переиспользуется или экспортируется. Задания включаются в экспорт по составу выбранной работы. Сам нативный префикс не включает строгие требования, а дополнительный `target="manual"` не нужен. Если конкретному адаптеру необходимы настройки обработки задания, они задаются явно и проверяются в контексте этого экспорта.

ID обозначает логический курс и задаётся один раз в корневом `_quarto.yml`. Он необязателен для обычного рендера. Сборщик передаёт его в контекст экспорта, где требуется устойчивый ключ. Это явная передача контекста инструментом курса: штатного наследования между самостоятельными Quarto-проектами не предполагается.

Ключ экспортируемого задания образуется из `course.id` и `exr-id`. Разные экспортируемые задания одного курса должны иметь разные ID; одно задание может входить в несколько работ. Обычные упражнения разных подпроектов сохраняют самостоятельные области ID и не включаются в экспортную проверку только из-за своего префикса.

Согласованный сценарий экспорта запускается из корня курса с выбором книги и работы. Работа использует задания своей книги. QRC связывает материалы переходами и не переносит тела внешних заданий в экспорт. Поддержка отдельного запуска экспорта непосредственно из вложенной книги не вводится.

Экспорт получает полные исходные данные выбранной работы независимо от проекции аудитории в опубликованном HTML и создаёт результат по требованиям адаптера. Публиковать `full` или предварительно готовить полный HTML не требуется. Функциональные профили и конфигурация задания учитываются. Ключи заданий и работ проверяются в единственном экспортном банке курса.

Полный экспортный корпус включает контрольные файлы, даже если они не входят в student-рендер. Условие для участника LMS отделено от приватного ответа и от наличия страницы на открытом сайте. Доступ к контрольной и показ ответов регулируются средствами PrairieLearn или Moodle; параметры доступа не превращаются в общие правила HTML-публикации.

Назначение `course-role` и сложность `difficulty` остаются необязательными при обычном оформлении и экспорте. Указанные значения проверяются. Экспорт также проверяет необходимые ему ответы, параметры работы и поддерживаемое содержимое; обязательность педагогических классификаций из этого не следует.

Параметры платформ — UUID, ID курса на сервере, попытки, назначения и доставка — остаются в адаптерной конфигурации. В обычном режиме оформления такие параметры не нужны.

Переход к этому контракту выполняется однократно на актуальных выпусках инструментов. Старые формы YAML, конфигураций и QMD не поддерживаются новой поставкой; версии авторского формата, aliases и режимы совместимости не вводятся. История Git и закреплённые теги расширений сохраняются для воспроизводимости. Изменение экспортной идентичности при миграции описывается явно и не превращается в постоянный обработчик прежнего контракта.

Перед реализацией на последних актуальных версионных ветках проводится анализ архитектуры, фактических зависимостей и организации кода, затем необходимый рефакторинг. Стандартные функции Quarto переиспользуются через публичные API. Спецификации, схемы, README, руководства и примеры обновляются согласованно с изменениями в соответствующих PR.

## Критерии нового контракта

- Обычный `exr-*` с нативной ссылкой рендерится в книге, статье и Revealjs без обязательного owner, `target`, роли или сложности.
- `exm-*` и `exr-*` сохраняют разные значения Quarto; автор не меняет тип ради отключения экспортной проверки.
- Явно добавленные учебные атрибуты проверяются как атрибуты расширения.
- Выбранный экспорт проверяет устойчивые ключи, состав, ответы и поддерживаемое содержимое; ошибка экспорта не выдаётся как запрет обычного нативного элемента.
- ID логического курса не дублируется искусственно в каждом подпроекте; способ передачи контекста определён явно.
- Ключ задания стабилен при переносе файла внутри того же курса; конфликт разных экспортируемых заданий диагностируется, а включение одного задания в несколько работ допустимо.
- Работа экспортирует задания своей книги; обычная ссылка QRC на другой проект не включает импорт тела задания.
- `student/full` сохраняют одни исходники, условия и устойчивые ID общих задач; дополнительные контрольные файлы определяются штатными списками профилей и включаются в полный исходный вход экспорта.
- Экспорт содержит необходимые данные выбранной работы при наличии только студенческой публикации и не требует публикации полного курса.
- HTML и Revealjs могут относиться к одному логическому курсу, сохраняя собственные нативные результаты сборки.
- Прежние экспортные ключи сохраняются либо имеют явную миграцию. Изменение курса-владельца и простое перемещение файла различаются.

Обзор проверен по исходникам, спецификации, истории и документам Quarto. Исполнение изменённого контракта ещё не реализовано и не проверялось сборками.
